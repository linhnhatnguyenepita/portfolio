1. Prérequis sur votre machine

Vous avez reçu deux fichiers : mon .env déjà rempli et ma clé privée SSH de déploiement (le fichier dont le chemin figure dans VPS_SSH_KEY_FILE). Tout est donc déjà en place : les secrets GitHub sont poussés et le VPS est déjà provisionné.

⛔

Ne lancez PAS make gen-secrets, make secrets ni make provision : ces étapes génèrent les secrets et configurent le VPS — elles ont déjà été faites. Les relancer écraserait des secrets existants.

Outils à installer côté contrôleur (votre poste, sous Linux Debian/Ubuntu) :

# Outils de base (Ansible, make, client SSH, curl)
sudo apt update
sudo apt install -y ansible make openssh-client curl

# Collections Ansible utilisées par les playbooks
ansible-galaxy collection install community.docker community.general
🐧

Sur Fedora/RHEL : sudo dnf install -y ansible make openssh-clients curl. Sur Arch : sudo pacman -S ansible make openssh curl. Si apt fournit une version d'Ansible trop ancienne, utilisez python3 -m pip install --user ansible-core.

2. Démarrer le workflow avec le .env et la clé SSH

Toutes les cibles make chargent automatiquement le .env à la racine du dépôt. Il suffit de déposer les deux fichiers reçus au bon endroit, puis de déployer.

  1. Déposer le .env à la racine du dépôt

    cp /chemin/vers/.env  ./.env

    Le fichier .env est gitignoré : il ne sera jamais committé. Il contient notamment VPS_HOST, VPS_USER, GH_REPO et le chemin VPS_SSH_KEY_FILE.

  2. Déposer la clé privée SSH à l'emplacement attendu

    mkdir -p ~/.ssh
cp /chemin/vers/vps_deploy_key  ~/.ssh/vps_deploy_key   # = chemin VPS_SSH_KEY_FILE
chmod 600 ~/.ssh/vps_deploy_key                      # Ansible/SSH refusent une clé trop permissive
    ℹ️

    Le chemin local de la clé est celui de VPS_SSH_KEY_FILE dans le .env (par défaut ~/.ssh/vps_deploy_key). S'il diffère, déposez la clé exactement à cet emplacement-là, ou ajustez la variable.

  3. Déployer l'application et le monitoring

    make deploy        # (re)déploie l'application sur le VPS
make monitoring    # déploie la stack Prometheus + Grafana
make tunnel        # tunnel SSH -> Grafana (3001) + Prometheus (9090)

    Ces cibles utilisent la clé de déploiement (VPS_SSH_KEY_FILE) pour se connecter au VPS en tant qu'utilisateur deploy.

✅

Observer la chaîne CI/CD complète sans rien déployer à la main : un git push sur main (ou Run workflow depuis l'onglet Actions) déclenche CI → Security → SonarCloud, puis le workflow Deploy quand la CI passe. Les secrets GitHub étant déjà configurés, le pipeline tourne tel quel.

4. Les commandes make

Le Makefile est une façade autour des scripts et des playbooks Ansible. Chaque cible source automatiquement le .env. make help liste toutes les cibles. Voici ce que chacune fait :

make gen-secrets setup initial

Exécute scripts/gen-secrets.sh. Génère, uniquement si la valeur est encore vide (idempotent) : un mot de passe Grafana aléatoire (GRAFANA_ADMIN_PASSWORD), une paire de clés SSH ed25519 à VPS_SSH_KEY_FILE, et la clé publique correspondante dans SSH_PUBKEY. Tout est réécrit dans le .env.

make secrets setup initial

Exécute scripts/set-github-secrets.sh. Pousse en une fois les secrets GitHub Actions du dépôt (GH_REPO) via la CLI gh : les valeurs simples lues dans le .env + la clé privée VPS_SSH_KEY (lue depuis le fichier). Nécessite gh auth login.

make provision une seule fois

Lance ansible/provision.yml pour bootstrapper un VPS neuf : installe Docker, crée l'utilisateur deploy (avec SSH_PUBKEY), les dossiers /opt/portfolio et /opt/monitoring, et le firewall UFW. Se connecte avec VPS_BOOTSTRAP_USER (par défaut ubuntu chez OVH).

make deploy

Lance ansible/deploy.yml : connexion à GHCR, pull de l'image ghcr.io/.../portfolio:$IMAGE_TAG (défaut latest), arrêt de l'ancien conteneur, démarrage du nouveau sur le port 3000 avec le /opt/portfolio/.env du VPS.

make monitoring

Lance ansible/monitoring.yml : rend les configs Prometheus/Grafana, démarre la stack via docker-compose, puis vérifie que Prometheus est prêt et que toutes ses cibles sont up (échoue sinon).

make tunnel / make tunnel-stop

Ouvre (en arrière-plan) un tunnel SSH multiplexé redirigeant Grafana (3001) et Prometheus (9090) vers localhost, en utilisant VPS_SSH_KEY_FILE. tunnel-stop le referme.

5. Comment fonctionne le CI/CD

Quatre workflows GitHub Actions dans .github/workflows/. Sur un push vers main (ou une pull request), CI, Security et SonarCloud tournent en parallèle. Le workflow Deploy ne se déclenche qu'après une CI réussie.

git push main → CI Security SonarCloud → CI ✅ → Deploy

ci.yml — intégration continue

Quatre jobs parallèles, avec Bun : Lint (bun run lint), Type check (bun run typecheck), Build (bun run build avec les variables Sanity), et Docker build (construction de l'image sans push, pour valider le Dockerfile).

deploy.yml — déploiement continu

Déclenché par workflow_run à la fin du workflow CI sur main — et seulement si la CI a réussi — ou manuellement via workflow_dispatch. Étapes :

  • Checkout du SHA exact qui a passé la CI ;
  • Build + push de l'image vers GHCR, taguée latest et avec le short SHA du commit (cache GitHub Actions activé) ;
  • Installation d'Ansible, écriture temporaire de la clé VPS_SSH_KEY ;
  • Exécution de deploy.yml (avec image_tag = short SHA) puis de monitoring.yml ;
  • Suppression de la clé privée (if: always()).
🧭

Le tag d'image dérive du short SHA, identique des deux côtés (workflow et playbook) : le VPS pull donc exactement l'image construite pour ce commit. La concurrency est configurée pour ne jamais annuler un déploiement en cours (les déploiements se mettent en file).

6. Sécurité & qualité du code

security.yml — analyse de sécurité

Sur PR, push main, et tous les lundis 06:00 (cron). Principe du moindre privilège (permissions read par défaut). Cinq jobs :

Les résultats SARIF (CodeQL, Trivy) remontent dans l'onglet Security du dépôt GitHub via upload-sarif.

sonarcloud.yml — qualité du code

Sur PR et push main. Checkout complet (fetch-depth: 0, requis pour le blame et la détection du code neuf), installation des dépendances avec Bun, puis scan SonarCloud (qualité, bugs, code smells, couverture, sécurité) via le secret SONAR_TOKEN.

7. Comment fonctionne le monitoring

La stack d'observabilité est déployée par monitoring.yml (manuellement via make monitoring, ou automatiquement par le workflow Deploy). Elle tourne en docker-compose dans /opt/monitoring sur le VPS.

  • Prometheus — collecte les métriques toutes les 15 s. Cibles scrappées : prometheus lui-même, node-exporter (métriques de l'hôte) et cadvisor (métriques par conteneur).
  • Grafana — deux dashboards provisionnés automatiquement : Host — Node Exporter (CPU, mémoire, disque, réseau) et Containers — cAdvisor (ressources par conteneur, dont portfolio).
  • node-exporter et cAdvisor — exportateurs scrappés par Prometheus.
🔐

Tous les ports de monitoring sont bindés sur 127.0.0.1 et accessibles uniquement par tunnel SSH. Le playbook échoue si GRAFANA_ADMIN_PASSWORD n'est pas défini, et vérifie en fin de run que toutes les cibles Prometheus sont up.

Accès manuel à Grafana sans make tunnel :

ssh -L 3001:127.0.0.1:3001 deploy@<VPS_HOST>
# puis ouvrir http://localhost:3001 — login admin / $GRAFANA_ADMIN_PASSWORD

8. Comment fonctionne Ansible

Trois playbooks dans ansible/, chacun ciblant le groupe vps de inventory.ini. La configuration (ansible.cfg) désactive le host key checking et utilise une sortie YAML lisible.

provision.yml une fois, en sudo

Bootstrap d'un VPS Debian/Ubuntu neuf, en become: true : ajout du dépôt APT officiel de Docker, suppression des paquets Docker de la distro qui entrent en conflit, installation de Docker Engine, création de l'utilisateur deploy (groupe docker, clé SSH_PUBKEY autorisée), création de /opt/portfolio et /opt/monitoring, scaffold d'un .env runtime, et firewall UFW (deny par défaut, autorise SSH + port 3000).

deploy.yml connexion deploy, sans sudo

Login GHCR (via GHCR_USER/GHCR_PAT), pull forcé de l'image au tag demandé, suppression de l'ancien conteneur, puis lancement du nouveau : port 3000, restart_policy: unless-stopped, variables d'environnement depuis /opt/portfolio/.env.

monitoring.yml connexion deploy, sans sudo

Rend les templates Jinja (prometheus.yml, datasource & dashboards Grafana, docker-compose.yml) dans /opt/monitoring, copie les dashboards JSON, démarre la stack avec docker_compose_v2, puis vérifie que Prometheus écoute, est prêt (/-/ready) et que toutes ses cibles actives sont up.

🧱

Séparation des privilèges : provision.yml a besoin de sudo (installation système), tandis que deploy.yml et monitoring.yml se connectent en tant qu'utilisateur deploy (membre du groupe docker) sans sudo.
